# One API process on one SQLite file, with hand-written idempotent migrations

The platform runs as a single FastAPI process against one SQLite file (`sqlite:///./data/app.db` by default) through SQLAlchemy. There is no database server and no migration tool. At startup, `make_session_factory` creates any missing tables from the models, then runs a short list of hand-written migrations. Each migration inspects the live schema first and does nothing if its change is already there, so starting against a fresh, old or current database file all end in the same schema. A migration that SQLite cannot do in place, such as dropping `NOT NULL`, rebuilds the table and copies its rows inside one transaction. An Analysis Run builds its scoring rows in one transaction, which holds SQLite's write lock while Portfolios are scored and Research Tilts requested (ADR-0005). That transaction commits when the run's first Audit Event is written, and each later Audit Event commits on its own; the run becomes current only when its final commit marks it completed. A crash partway through therefore leaves a run that is never current and is marked interrupted at the next start, not a half-scored current run. What such a run still leaves committed is set out in ADR-0009.

## Considered Options

- **PostgreSQL plus Alembic from day one**: rejected for the demonstrator. It needs a database server to install, configure and seed before anyone can run the demo or the tests, and a migration history to maintain for a schema still changing ticket by ticket. It buys concurrent writers and row-level locking, which a demonstrator with a handful of users and one writer at a time does not need. SQLite already gives the scoring step its single transaction and the run its single point at which it becomes current, and the SQLAlchemy models are not tied to SQLite, so the move remains open.

## Consequences

Running the API needs only `uv` and a writable directory. Each test gets its own throwaway database file, and a reviewer can copy, inspect or delete the whole state as one file. The migrations have no version table and no downgrades: each one is safe to re-run and is checked against the schema it changes. Moving to PostgreSQL means switching to Alembic, with these functions as the baseline. The design also rests on single-process assumptions, which the architecture document's roadmap lifts by moving to PostgreSQL and an external progress store. First, Run Step progress and the one-in-flight check live in the process's memory (ADR-0005), so a second worker would neither see a run nor be stopped from starting another. Second, audit writes are serialised by an in-process lock (ADR-0002). A second process would compete for the chain's tail, and the unique `previous_hash` would reject the losing write rather than fork the chain. Third, SQLite allows one writer at a time, so the scoring transaction blocks Decisions and Insight Reviews for as long as it runs. That is why an LLM Exchange captured mid-run is written inside the run's own transaction, behind a savepoint (ADR-0004).
