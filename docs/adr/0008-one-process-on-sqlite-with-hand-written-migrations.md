# One API process on one SQLite file, with hand-written idempotent migrations

The platform runs as a single FastAPI process against one SQLite file (`sqlite:///./data/app.db` by default) through SQLAlchemy. There is no database server and no migration tool. At startup, `make_session_factory` creates any missing tables from the models, then runs a short list of hand-written migrations. Each migration inspects the live schema first and does nothing if its change is already there, so starting against a fresh, old or current database file all end in the same schema. A migration that SQLite cannot do in place, such as dropping `NOT NULL`, rebuilds the table and copies its rows inside one transaction. The scoring part of an Analysis Run is one transaction, so a crash leaves no half-scored run (ADR-0005). Audit Events are appended one at a time under a process-wide lock (ADR-0002). LLM Exchanges written mid-run go into the run's own transaction behind a savepoint (ADR-0004).

## Considered Options

- **PostgreSQL plus Alembic from day one**: rejected for the demonstrator. It needs a database server to install, configure and seed before anyone can run the demo or the tests, and a migration history to maintain for a schema still changing ticket by ticket. It buys concurrent writers and row-level locking, which a single-user demonstrator does not use. SQLite gives the same all-or-nothing scoring transaction, and the SQLAlchemy models are not tied to SQLite, so the move remains open.

## Consequences

Running the platform needs only `uv` and a writable directory. Each test gets its own throwaway database file, and a reviewer can copy, inspect or delete the whole state as one file. The migrations have no version table and no downgrades: each one is safe to re-run and is checked against the schema it changes. Moving to PostgreSQL means switching to Alembic, with these functions as the baseline. The design also rests on single-process assumptions, which the Roadmap lifts by moving to PostgreSQL and an external progress store. First, Run Step progress and the one-in-flight check live in the process's memory (ADR-0005), so a second worker would neither see a run nor be stopped from starting another. Second, audit writes are serialised by an in-process lock (ADR-0002). A second process would compete for the chain's tail, and the unique `previous_hash` would reject the losing write rather than fork the chain. Third, SQLite allows one writer at a time, so the scoring transaction blocks Decisions and Insight Reviews for as long as it runs. That is why an Exchange captured mid-run must be written through the run's own session.
