# 11. Risks and Technical Debt

This section lists the known gaps, so a reviewer does not have to find them. Each entry says what is true of the code on the baseline commit, what could go wrong, what limits the damage today, and where the [Target / Production Roadmap](13-roadmap.md#roadmap-items) closes it. Fixing these gaps is outside the scope of this version. Most of them are accepted because the platform is a single-process demonstrator on synthetic data ([2. Architecture Constraints](02-architecture-constraints.md)), and none of them is accepted for production.

**Severity** is rated for a production deployment, not for the local demonstrator:

| Severity | Meaning |
| --- | --- |
| **High** | Blocks a production go-live, or weakens one of the top three quality goals (Auditability, Explainability, Human control / safety) |
| **Medium** | Must be closed before production. A compensating control limits the damage today |
| **Low** | Known and contained. Close it when the surrounding code next changes |

## 11.1 Risks

| ID | Risk | Severity | Impact | Limits on the damage today | Mitigation |
| --- | --- | --- | --- | --- | --- |
| <a id="r-01"></a>R-01 | **No SSO or MFA.** Users sign in with a local username and password, hashed with scrypt. At startup the API creates one user per role, and all of them share the password in `APP_SEED_USER_PASSWORD`. `POST /api/auth/login` has no lockout or throttling, and a failed login writes no Audit Event | High | A guessed or phished password gives the full permissions of its role, with no second factor and no trace of the failed attempts. Joiners, movers and leavers are not managed against a corporate identity | scrypt hashing; only the SHA-256 of the session token is stored; sessions expire after `APP_SESSION_TTL_HOURS` (12 by default); logout deletes the session; every authorization decision is made on the server ([8.8](08-crosscutting-concepts.md#88-authentication-and-authorization)) | Federated sign-in with MFA, roles from directory groups ([Roadmap](13-roadmap.md#roadmap-items)) |
| <a id="r-02"></a>R-02 | **No CSRF token.** The session is an `HttpOnly`, `SameSite=Lax` cookie, and state-changing requests carry no anti-forgery token | Medium | A page on a *same-site* origin, such as a compromised sibling subdomain, could send state-changing requests with the user's cookie, for example a Decision or a configuration change | `SameSite=Lax` keeps the cookie off cross-site subrequests; CORS admits only `APP_CORS_ORIGINS` (`http://localhost:5173` by default); request bodies are JSON; every write is permission-checked and audited | Anti-forgery token or `SameSite=Strict`, set in the production profile ([Roadmap](13-roadmap.md#roadmap-items)) |
| <a id="r-03"></a>R-03 | **`Secure` cookie off by default.** `APP_COOKIE_SECURE` defaults to `false` so that the demonstrator runs over plain `http://localhost` | High | A deployment that forgets to set it sends the session token over any plain-HTTP hop, where it can be captured and replayed until it expires | The flag is one setting, listed in `.env.example`; `HttpOnly` keeps the token away from page scripts | TLS everywhere, and a production profile that will not start with the flag off ([Roadmap](13-roadmap.md#roadmap-items)) |
| <a id="r-04"></a>R-04 | **A single API process** ([ADR-0008](../adr/0008-one-process-on-sqlite-with-hand-written-migrations.md)). The one-in-flight check, Run Step progress and the audit write lock all live in the process's memory | High | No horizontal scaling and no failover. A second worker would not see the in-flight run and could start another one, and it would compete for the audit chain's tail. A restart interrupts any run in flight | Startup marks an unfinished run `interrupted`, so the one-in-flight check never sticks; the unique `previous_hash` rejects a competing audit write instead of forking the chain | Stateless API workers over a shared database and an external progress store ([Roadmap](13-roadmap.md#roadmap-items)) |
| <a id="r-05"></a>R-05 | **SQLite** ([ADR-0008](../adr/0008-one-process-on-sqlite-with-hand-written-migrations.md)). All state, including the audit chain, LLM Exchanges and Client PII, is in one file, with one writer at a time | High | The scoring transaction blocks Decisions and Insight Reviews while it runs. There is no backup, point-in-time recovery or replication, and no database-level access control or encryption at rest: anyone who can read the file can read everything in it | Idempotent migrations run at startup; the database file is git-ignored; at demonstrator scale the scoring window is short | Managed PostgreSQL with backups, encryption at rest and role-separated access, migrations moved to Alembic ([Roadmap](13-roadmap.md#roadmap-items)) |
| <a id="r-06"></a>R-06 | **In-process Run Step progress** ([ADR-0005](../adr/0005-run-step-progress-in-process.md)). The registry that feeds the Server-Sent Events progress stream is a Python object | Medium | Progress is lost on restart, and no other worker can serve it, so it blocks R-04's fix | The run row and its outcome are in the database; an interrupted run is marked as such at startup; each stream event carries the whole run state, so a reconnecting browser recovers from one event | External progress store, lifted with R-04 ([Roadmap](13-roadmap.md#roadmap-items)) |
| <a id="r-07"></a>R-07 | **Synthetic data** ([ADR-0003](../adr/0003-market-data-snapshot-synthetic-clients.md)). Clients and Holdings are generated by the seeder; market data is a committed snapshot, refreshed by hand | Medium | Nothing yet shows how the engine, the Grounding validator and the prompts behave on real Client data: its quality, its volume, or the wider range of real Reports. Stale prices put Asset-Class Drift, Portfolio Drift and Trade Lines out of date | Every Client is synthetic, so no real PII is held; the snapshot makes results reproducible; the engine is covered by deterministic tests | A data-protection review, then a controlled pilot on real data with a live market data feed ([Roadmap](13-roadmap.md#roadmap-items)) |
| <a id="r-08"></a>R-08 | **LLM provider dependency.** Live mode calls one OpenAI-compatible endpoint, OpenRouter by default, for the model of record `anthropic/claude-sonnet-5.5`. Each call has a 120-second timeout and no retry | Medium | If the provider is down or slow, Insight extraction, Research Tilts, narratives, memos and the Assistant fail. Report passages and engine figures leave the platform for a third party. A model or provider change can shift behaviour, and the eval has been run only on the model of record | The engine owns every number, trade and suitability verdict, so a failed AI step degrades to a rule-based Recommendation or a "Narrative unavailable" note; every failure is stored as an error LLM Exchange; prompts carry pseudonyms only ([QS-D1](10-quality-requirements.md#data-protection)); the endpoint is swappable by configuration; recorded mode runs with no provider at all | A gateway (LiteLLM) with fallback models and quotas, provider data-processing terms, and a live eval rerun on every model change ([Roadmap](13-roadmap.md#roadmap-items)) |
| <a id="r-09"></a>R-09 | **The audit chain has no external anchor.** Verify recomputes the chain from the rows in the database ([ADR-0002](../adr/0002-hash-chained-append-only-audit-log.md)) | High | An edit to one event is detected ([QS-A1](10-quality-requirements.md#auditability)). But someone with write access to the database file who rewrites an event, and then recomputes every later hash and every referenced Exchange hash, produces a chain that verifies | No API updates or deletes events; the database file is outside the repository; the tamper tests cover single edits, deletions and broken links | Write the chain head regularly to write-once storage or an external timestamping service, and verify against it ([Roadmap](13-roadmap.md#roadmap-items)) |

## 11.2 Technical debt

| ID | Debt | Severity | Impact | Limits on the damage today | Mitigation |
| --- | --- | --- | --- | --- | --- |
| <a id="td-01"></a>TD-01 | **No structured logging, metrics or tracing.** The only application logging is a few standard-library log lines in `app/analysis_runs.py`, for a failed or interrupted Analysis Run | Medium | No request logs, latency or error-rate metrics, LLM cost or latency dashboards, or traces across the SPA, the API and the provider. Operations cannot see trouble before users report it | The audit chain and LLM Exchanges record every business event, AI call, tokens and latency; the Health screen reports database, market data and LLM status. These are evidence, not telemetry | Structured JSON logs with request ids, metrics and OpenTelemetry traces ([Roadmap](13-roadmap.md#roadmap-items)) |
| <a id="td-02"></a>TD-02 | **No frontend test runner.** CI runs eslint, prettier, `tsc` and a Vite build on the SPA, but no unit, component or end-to-end tests | Medium | A screen regression, for example a Decision button that posts the wrong action, is caught only by hand | Every rule the UI shows is enforced and tested again at the API seam, so a UI bug cannot grant a permission or skip an approval; the API types are generated from the OpenAPI schema; `docs/manual-e2e-checklist.md` is walked before a release | A component test runner and browser end-to-end tests in CI ([Roadmap](13-roadmap.md#roadmap-items)) |
| <a id="td-03"></a>TD-03 | **An unanchored Research Tilt LLM Exchange.** When a tilt is assessed but the rebalance plan yields no Trade Lines, no Recommendation is drafted, so no `research_tilt_proposed` event references the Exchange ([6.1](06-runtime-view.md#61-analysis-run)) | Low | The Exchange is stored but not referenced by any Audit Event, so verify does not check it. This is the one exception to [QS-A2](10-quality-requirements.md#auditability) | The Exchange still commits with the scoring transaction and is visible to `llm:read` roles; nothing downstream uses the tilt | Write a tilt Audit Event whether or not a Recommendation follows ([Roadmap](13-roadmap.md#roadmap-items)) |
| <a id="td-04"></a>TD-04 | **Research Tilt Exchanges are rolled back with a failed scoring phase.** They are stored under savepoints inside the scoring transaction ([ADR-0008](../adr/0008-one-process-on-sqlite-with-hand-written-migrations.md)), so a failure in Load inputs or Score Portfolios discards them ([6.1](06-runtime-view.md#61-analysis-run)) | Medium | The provider received those prompts, but the platform keeps no record that the calls happened. That is a gap in LLM call evidence | Nothing the calls produced survives either: no score, tilt or Recommendation; the run row stays with outcome `failed` | Capture Exchanges in their own transaction, made possible by the move to PostgreSQL ([Roadmap](13-roadmap.md#roadmap-items)) |
| <a id="td-05"></a>TD-05 | **Analysis Run recording commits once per Audit Event** ([ADR-0009](../adr/0009-analysis-run-recording-commits-per-audit-event.md)) | Medium | If the process dies during `record_run`, an interrupted run can leave Recommendations open to a Decision with an incomplete audit trail | The run is never current and is marked `interrupted`; ADR-0009 tells reviewers to treat such a run's Recommendations as suspect | The deferred atomic-recording fix in ADR-0009 ([Roadmap](13-roadmap.md#roadmap-items)) |
| <a id="td-06"></a>TD-06 | **The recording key omits the model.** A recording is keyed by task, prompt version, system text, schema and input, not by `APP_LLM_MODEL` | Low | After a model change, recorded mode keeps replaying replies from the earlier model without saying so, so tests and demos can mask a change in behaviour | A comment in `.env.example` says to re-record after changing the endpoint or model; the committed recordings are from the model of record | Add the model to the key, so a model change misses instead of replaying ([Roadmap](13-roadmap.md#roadmap-items)) |
| <a id="td-07"></a>TD-07 | **Hand-written migrations** ([ADR-0008](../adr/0008-one-process-on-sqlite-with-hand-written-migrations.md)) have no version table and no downgrades | Low | A schema change cannot be rolled back, and the state of a database can only be inferred from its schema | Each migration is idempotent, checked against the schema it changes and tested on an existing database | Alembic, with these functions as its baseline, as part of R-05 ([Roadmap](13-roadmap.md#roadmap-items)) |
